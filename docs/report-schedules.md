# Report generation schedules

The owner opens **Properties → Report schedules** and records a report kind, property, optional financial beneficiary, basis, IANA time zone, starting month, local day from 1 to 31 and local hour. A configured day beyond month end uses that month’s last day. Type **GENERATE ONLY** to record consent. The existing hourly Cron checks the due window. A month is generated once even with concurrent or repeated ticks; generation covers the preceding calendar month. A late tick in the same month catches up; a missed prior generation month is not backfilled.

Financial, rent roll, delinquency, vacancy and maintenance reports use their existing readers. Owner filters are available for financial schedules. A close-required schedule remains eligible until the preceding period closes. Reopening that period invalidates its generated link. Retire the old schedule and save new reviewed terms to change it.

Generation receipts retain the format version, date window and SHA-256 fingerprint. They retain no report contents or recipient credentials. **Open verified current report** requires the configuring owner to remain the signed-in installation owner, a live property read and unchanged source fingerprint. It refuses retirement, lost authority, reopened periods and changed report sources. A restore preserves receipts but grants no configuring authority to the destination owner. API credentials and staff are refused. The generated view is not an immutable delivered artifact: source changes require a new report review.

Commands are `report.schedule`, `report.retire` and `report.generate`. The private JSON doors are `GET /api/report-schedules` and `GET /api/report-generation?id=ID`. Manual generation uses the same due checks as Cron. The scheduler configures no recipients and sends no email. Generation never authorizes a send. ## Reviewed owner statement links

For a financial generation filtered to one owner, choose that person's existing active owner portal grant and type **DELIVER OWNER REPORT** with an authorization reference. This freezes the existing portal allocation statement for the scheduled property and date window, with its SHA-256. It does not expose the staff financial report or grant additional access. Review the frozen statement, then type **SEND LINK** with a send authorization reference. Each submission rechecks the configuring owner, schedule, close requirement, current report sources, recipient grant and ownership periods.

The email contains only a link requiring that exact person's live portal session and grant. It carries no bearer sign-in token and no report contents. The recipient reads the frozen statement, never a newly substituted report. A changed ownership scope or statement contents, retirement, reopened required close, a bounced report or revoked access makes the link unavailable. The ordinary portal statement remains available according to existing rights.

A durable uncertain claim is committed before contacting the installation mail provider. Concurrent requests cannot send twice. Provider acceptance is not mailbox delivery. Accepted and uncertain outcomes cannot be resent. A definite rejection, rate limit, development suppression or missing configuration permits an explicit retry after fresh source and authority checks, using the same provider idempotency identity. After provider acceptance, staff may record delivered or bounced with a provider evidence reference. A bounce creates a visible failed-delivery next action and disables the link; this is staff-recorded evidence, not an automatic provider callback. Interrupted or ambiguous sends stay uncertain for reconciliation; automatic reconciliation is not implemented.

Private delivery snapshots, recipient references and delivery events stay in the installation and are excluded from backup and readable export. Restore preserves generation receipts but restores no delivery link or authority, and sends nothing. Retention default ADOPTED: snapshots remain until the owner explicitly deletes them through an audited path; legal and accountant holds block deletion until released.

## Snapshot retention and holds

Snapshots remain in the installation until its owner explicitly deletes them. In the existing delivery card, **Place snapshot hold** records either a legal or accountant hold with a reference. **Release snapshot hold** records the release reference, actor and time. Each hold must be released independently. An active accounting or all-record legal hold on a tenancy in the statement property also blocks deletion through the existing privacy hold door.

**Delete snapshot** requires **DELETE SNAPSHOT** and a deletion reference. The atomic command checks active holds and the current revision, clears the stored statement bytes, marks the link unavailable and records the action in history. A minimal delivery receipt, checksum, send identity and custody audit remain in the installation so deletion cannot authorize another send. No scheduler deletes snapshots. Retention and release references are not new recipient fields. Snapshots, delivery records and their holds and events are excluded from backup and readable archives.

Commands are `report.delivery.hold` (`deliveryId`, `kind` legal or accountant, `reference`), `report.delivery.release` (`deliveryId`, `holdId`, `reference`) and `report.delivery.delete` (`deliveryId`, `consent` DELETE SNAPSHOT, `reference`). Only a signed-in installation owner may use them; staff and API credentials are refused.
