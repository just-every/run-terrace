# Integrations and persistent operating automation: exact terms

The exact terms of the clauses in the “Integrations and persistent operating automation” area of [CONTRACT.md](../../../CONTRACT.md). Each clause there is the requirement; the terms below define it.

## OPS-001 — Expose a scoped property operations API

**Exact semantics (done 21 October 2026):** a credential belongs to one staff role and a fixed set of portfolios (or all) and has scope `read` (GET only) or `prepare` (GET plus the listed proposal commands: maintenance.prepare/revise, quote.add, renewal.prepare, arrears.prepare, correction.prepare, charges.preview, agent.execute); any command not on that list, and every approval, owner decision, period or access command, is refused (403 `credential_cannot_approve` or `credential_scope`) so a future approval, payout, send or connection door is closed to credentials until it is deliberately listed with its own acceptance; a role the credential's role lacks answers 403 `forbidden`. Tokens (`ttk_…`) are shown once, stored only as a SHA-256, never archived or exported, and the owner mints, rotates (the old token stops at once) and revokes them under the fresh email-link proof; credentials carry no session, so they never pass a second factor and never open a page, backup or readable export. Version 1 lists (`/api/v1/{properties,leases,households,ledgers,owner-ledgers,documents,work,reports}`) are scoped before paging, sorted by id, with `limit` 1 to 200 (default 50) and an opaque `cursor`; an out-of-scope record is 404. Every credential write needs an `Idempotency-Key` (8 to 100 characters): the same key and body replays the stored response once (`idempotent-replay: true`), the same key with another body is 422, and a key whose first attempt never reported back stays pending (409) rather than being run again. Any error after the key is claimed retains it as pending, including failure to persist the response after a domain commit; restart never releases it. History names the credential, its role version and scope. Each future resource (PORT-007 documents, ACCT-012 statements, PORTAL-010 notices) and command door joins `/api/v1` with the same scoping before it ships.

## OPS-003 — Run persistent workflow templates

**Exact semantics (ct 22 October 2026; hourly sweep and send recording built in the OPS-003 fix round):** a template version (kind leasing, renewal, rent, delinquency or unit turn) holds a kind-specific trigger (renewal: days before the lease ends; leasing: days an enquiry has had no activity; rent: 1–30 days past due; delinquency: 31+ days past due; unit turn: an open make-ready board), optional conditions (one property; a minimum overdue amount), 1–12 steps (task, contact or gate; each with a due-day offset and an optional assignee), one contact limit for the whole run (1–10 attempts), and the owner or portfolio manager an escalation goes to. Only the owner and every-portfolio managers configure; a change appends a version and runs keep the version they started under. A run starts for one record only when it matches the trigger and conditions inside the person's portfolios and holds the existing action for that kind of record (leasing: prospect.respond; renewal: renewal.reply; rent and delinquency: arrears.prepare; unit turn: turnover.task.update); a person starts it, or a sweep starts the runs the triggers call for, once per record and template. The sweep runs unattended every hour (a Cron Trigger) and on demand (Run now, by the owner or an every-portfolio manager). The unattended tick acts as `scheduler:workflows`, attributed to the person who saved the template version, with no session. It is fenced on that person still being the owner or an every-portfolio manager; a template that fails the fence starts nothing and is listed as needing a configurer, and its running or paused runs escalate to the owner with a durable next action. A tick only starts runs, escalates overdue steps and runs WORK-010's maintenance scheduler (its orders still await owner or admin approval). It never records an attempt, reply, evidence, resumption or closure. Each tick is recorded (time, runs started, steps escalated, templates skipped), and a replayed or concurrent tick starts or escalates nothing twice. Every transition appends a sequenced event and rewrites the run's durable next action in D1, so a restart loses nothing. Task steps finish with an evidence reference; contact steps record each attempt (channel, outcome, external reference) and then the reply; gate steps finish only when Terrace already holds the fact (the make-ready board is published ready, the renewal is executed, the prospect is leased, the overdue balance is cleared). A run completes only when its last step has recorded evidence. A run pauses, writing nothing else, when the starter's or last resumer's role changed or ended, its assignee may no longer work it, its record changed or already reached its outcome, or a contact attempt's result is uncertain; a manager reviews and resumes (an uncertain result needs a stated delivered or not-delivered). A run escalates to the named person (the owner if that person no longer reaches the portfolio) when a step passes its due day (found by the sweep), when the contact limit is used up without an agreed reply, or when a reply is declined or unclear; an escalated run takes no further step and a person closes it (closed, never completed) or records the agreeing reply. Contact (ct, 22 October 2026): the workflow engine sends nothing itself, and staff record attempts and replies. A LEASE-005 prospect email, or a LEASE-012 approved renewal-offer send, made while a matching run is live for that record is recorded on the run as its next attempt. The email event is the external reference and the provider's answer is the outcome: accepted counts as sent and awaiting a reply; an uncertain answer for any recipient pauses the run; rejected, rate-limited, unreachable, suppressed or unconfigured is listed but does not count toward the limit. A send while the run is paused or escalated is listed on the run for the reviewing person and changes nothing else; a prospect's refused contact channel (LEASE-005) refuses the attempt; run labels carry no resident names; API credentials cannot run any workflow command. Future clauses inheriting this: WORK-010 (the unattended maintenance scheduler), PORTAL-005, COM-001 and NOTIFY clauses (a Terrace-sent contact must use a contact step, its consent and the same limit), OPS-002 (events for run transitions), AUTO-001 agents (prepare-only, never a step).

OPS-003 send grouping and recovery semantics: one explicitly requested renewal-offer send is one attempt across its recipient emails; every email event and per-recipient provider outcome is kept, and any uncertain recipient pauses the run. A slot is reserved in the same transaction as the source send event, preventing overlapping sends from bypassing the limit. Known non-sends release that reservation without consuming a contact. If a process ends before the provider result is recorded, the reservation survives and further workflow work is refused until a manager reviews the source and records delivered/not delivered through Review and resume; that unresolved attempt consumes its reserved slot. A later provider answer is still kept, never counted twice, and a contradictory answer pauses the run for review. The sweep's property-local date comes from its scheduled instant; Cron receipt identity is that UTC instant. The active installation owner authorizes WORK-010's unattended orders, prepared as `scheduler:workflows`, with no approval or dispatch.

## OPS-007 — Respect adjacent property product boundaries

Exact semantics (20 October 2026, ct ruling): the sibling decides access for the person. The installation owner alone enters each sibling product’s https origin (a host name; never an address literal, localhost, credentials, path, query or fragment). An owner or portfolio manager within the property’s portfolio links a property to a record address on that configured origin with a label; anyone who reads the property (existing scope) sees its links, and others get not-found. Terrace stores only the origin and the record’s address and label, never guest, booking, reservation, file or pipeline data; following a link opens the sibling, where the person’s own Cabin or Chest sign-in and grants decide access, and Terrace adds no credential and never vouches for the person. Each link is labelled as unchecked. An owner-configured installation credential may later confirm only that the record exists and show its title/status label (never exported), but owner-entered origins are outbound destinations under the egress rule, so that confirmation waits on Base’s egress door. Links change no residential ledger, statement or export record.
