# Card collection in Stripe test mode

Full residents open Pay by card from their lease account. Delegated contacts cannot collect or inspect card outcomes. Staff with the existing rent-receipt responsibility use Online card payments on the scoped ledger. Both doors retain the accepted consent wording, revision, actor and time with the frozen payment amount, refuse stale wording revisions, and require explicit one-time consent and the same PAY-005 lease policy, reviewed property rules, delinquency stage, charge priority and atomic pending reservation. Permitted excess remains separately identified credit; it is never automatically spent.

The payer fee is zero. The entered payment amount is the complete payer total; the property absorbs processing fees. Stripe-hosted Checkout collects the card and any required authentication. Terrace receives no card number or security code. Terrace disables adaptive currency conversion and Link for these USD sessions and requests no mandate or saved-card authorization. ACH and autopay remain separate clauses.

Configure the server binding `STRIPE_SECRET_KEY` with an authorized Stripe test secret. Never put it in source, a file or a browser bundle. Live credentials are refused. Hosted Checkout requires no publishable key in Terrace. Register the installation’s `/api/stripe/events` endpoint for `checkout.session.completed`, `checkout.session.expired` and `payment_intent.payment_failed` notifications. The body supplies only an event id: Terrace retrieves the canonical event directly from Stripe with its server credential, then verifies test mode, the stored session, metadata, currency, amount, successful intent and charge. It does not trust a posted amount or browser return and does not claim to verify a webhook signature.

A successful verified event posts the frozen charge allocations once and retains the provider event, session, payment and charge ids. Staff can verify an event from the ledger when reconciling provider delivery. The resident’s payment detail is a receipt only after that event. Declines post no receipt and remain retryable in the same Stripe session; a verified expiry releases the reservation. Replayed events, including concurrent delivery and process restart, add no second receipt. A definitive Checkout creation rejection releases its reservation; an uncertain creation stays held for provider reconciliation and is never automatically retried.

Staff see the provider’s fee and net when available. These figures and the ledger receipt are not evidence of a bank deposit. Deposit collection, separate deposit liability and routing Stripe settlement into the correct mapped deposit or rent-trust bank remain open PAY-003 points. The inherited PAY-005 policy remains CT-held. Card collection is PARTIAL.

Native backup and readable export preserve financial allocations and provider references. Hosted Checkout links and provider credentials do not transfer; a restored installation cannot replay collection or provider posting for an originating installation’s attempt. Pending restored attempts require originating-provider reconciliation.

Run the public-door integration journey through the PAY-003 registration in `tests/terrace.test.mjs`; its provider fake exists only at the network edge. Run `tests/card-payments-live.mjs` through the heavy slot with the held Stripe test credential injected into the process environment to exercise actual hosted success, decline, required authentication and event replay. It prints object ids only and captures resident and staff pages at 1440 and 390 pixels.

Stripe’s [Checkout fulfillment guide](https://docs.stripe.com/checkout/fulfillment) explains authoritative payment completion, and its [test-card guide](https://docs.stripe.com/testing) supplies the sandbox card scenarios.

## Recover an interrupted payment

Open **Rent & arrears**, choose the original tenancy, and inspect **Payment recovery worklist**. Each case retains the original payment, known session and canonical event, outcome, responsible person and next action. It is created with the pending reservation before contacting Stripe. An interrupted or failed acknowledgment stays unknown across Worker restarts.

Choose **Inspect original Stripe outcome** and supply the original session id from Stripe. This performs a fixed-origin read and checks the original payment, amount, currency, test mode and session. It never creates Checkout, repeats a provider write, releases a reservation or posts funds. Unknown or conflicting evidence stays visible and held. Choose **Assign recovery next action** to take responsibility and record the next step.

To apply an outcome, supply its canonical Stripe event id. The existing verifier retrieves the event and checks its exact original payment, session, successful intent and charge before posting the frozen allocations once. A failed database acknowledgment rolls the whole financial change back; the same canonical event can then reconcile after restart. Current staff responsibility and portfolio scope still apply. Existing consent and policy admission are retained, with no new payment authority.

Backup carries recovery evidence and assignments. Restored cases have no originating Checkout authority and cannot collect or post in the destination, even when its own Stripe configuration exists. Dispatch-provider lookup, scheduled actions, other payment rails and measured reference-deployment recovery objectives remain unfinished under SAFE-006.
